UI / UX Design Review

The Tickle status menu,
rebuilt to be read at a glance.

Tickle drops out of a menu-bar icon into a dropdown of live interview timers. Today every timer is a single dense line of ·-delimited text with its controls buried in a submenu. This review keeps the exact same data and rebuilds the row as a scannable, self-documenting object.

SurfaceNSMenu attached to an NSStatusItem
ScopeDropdown rows, hierarchy & row actions
CenterpieceCustom NSMenuItem.view rows with a tick-marked progress timeline
ConstraintSame model, same data — no new state

1

A tick-marked progress timeline

The core concept — N interval marks across a window — is now visible. Nine notches sit on the bar; fired marks light up, the playhead shows the live position. "3/9" stops being a number you decode.

2

Controls surface on hover, not in a submenu

Stop and Reset were one level deep behind a › disclosure. They now appear inline on hover as tap targets, so the primary destructive/soft actions are discoverable and one click away.

3

Two-tier typography replaces the delimiter wall

A bold primary line (time & ticks) carries what changes every second; a dimmed second line holds the fixed config (interval, sound, window). Scanning three timers no longer means parsing three identical · strings.

4

State becomes color, not emoji

A colored accent dot encodes state at the row's leading edge — green running, orange upcoming, gray done, red stopped — replacing the ✅ / ⏹ glyphs that read inconsistently across the menu.

5

Section headers carry a live count

Each header gains a matching state dot and a count pill, so "how many are running right now" is answerable without counting rows — reinforcing the grouping the current build already sorts into.

6

Stop all / Reset all live in a persistent footer

Today they only appear with 2+ timers and blend into the plain list. A pinned two-button footer gives them a stable home and a clear destructive treatment on Reset all.

02

What it takes in AppKit

The redesign stays inside NSMenu — no popover rewrite. Each timer row becomes a custom NSMenuItem.view, which is the sanctioned way to put rich content and hover controls into a menu.

Custom-view menu rows

Replace the single NSMenuItem(title:) per timer with an item whose .view is a lightweight NSView subclass that draws the two text tiers, the progress track, and the hover action buttons. The submenu goes away entirely.

Step 01
Build a TimerRowView

An NSView (~52pt tall) laid out with a stack view: accent dot, title/badge row, a custom-drawn progress bar, and the muted config line. Assign it via item.view = rowView in addSection().

Step 02
Draw the tick timeline

A small NSView whose draw(_:) strokes the track, fills to elapsed / windowSeconds, then dots each mark at i/totalMarks, brightening marks ≤ marksElapsed. All data already exists on TickTimer.

Step 03
Hover-reveal the actions

Add an NSTrackingArea; on mouse-enter unhide two NSButtons wired to the existing stopTimer(_:) / resetTimer(_:) selectors with the timer as representedObject. Highlight state comes from enclosingMenuItem.isHighlighted.

The live-update path barely changes. The existing 1s update() loop already re-titles every row; instead it calls rowView.refresh(timer) to re-fill the bar and relabel. Because the geometry (row count & sections) is unchanged, the sectionSignature() rebuild trigger stays exactly as is — only the per-row rendering is richer.
